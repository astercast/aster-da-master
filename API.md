# Aster da Master — API

## Shared API conventions (all sites)
- Base: `data/v1/` relative to the site root. Works on any static host; no auth, no keys, no rate limits.
- Manifest: `data/v1/index.json` lists every endpoint with its schema URL, `updated` timestamp, and notes. Start here.
- Timestamps: ISO-8601 UTC (`2026-10-11T00:00:00Z`). Date-only fields are `YYYY-MM-DD`.
- Versions: `meta.version` semver on the manifest; breaking changes get a new `v2/` path, never a silent shape change.
- Errors: static files can't return error bodies. A missing endpoint means a wrong path — re-read `index.json`. Empty results are `[]`, never `null`. Every record carries its provenance (`source`, `observed`/`updated`).
- Pagination: not needed — payloads are complete snapshots sized for client-side filtering. If a future endpoint paginates, it will use `?page=` and document it here.
- Freshness: every payload states when it was generated and from what snapshot. Treat undated numbers as stale.

Base: `data/v1/`. Static JSON, versioned. The artist record is the single source
of truth; `data/artist.json` feeds the site renderer and mirrors it.

- `data/v1/index.json` — manifest: version, endpoints, observation date, provenance, agent routing
- `data/v1/transmission.json` — the guided-journey aggregates: six eras (2018→2026) with transmissions, plays, sessions, distributor counts, top 3 tracks (with release pages), key sessions (deep-dive links where they exist), in-era collaborators, milestones, and computed "signal" one-liners; the 2026 (The Return) era carries an `extras` block (the four verified 2026 singles, the Q4 2026 Uncle-LP/trilogy watch, the play-count snapshot); drives `transmission.html` — the flagship journey is 13 stops: the six eras plus seven live data chapters (The Race, The Record Book, The Codex, The Architects, The Seasons, The Deep Cuts, The Horizon), all rendered from the real data/v1 JSON at load time (schema: `data/v1/schema/transmission.json`)
- `data/v1/network.json` — the collaboration network: artist-centered graph of the 21 title-credited collaborators (from `circle.json`) + producer scene figures (from `scene-figures.json`); nodes carry track lists, dates, deterministic layout positions; edges are track-weighted, with co-credit edges for collaborators sharing a track title; computed `insights` (most frequent collaborator, producer with most credits, busiest collab year, first-ever collaborator). Generated by `scripts/build_network.py`; drives `network.html` (schema: `data/v1/schema/network.json`)
- `data/v1/eras.json` — era deep-dives: the six eras with everything `transmission.json` carries PLUS the full era transmission list (every entry, with plays + release-page link), ALL in-era collaborators (`transmission.json` keeps only the top 3), the codex families active in the era, and a computed `summary` (ranks, archive-play share, busiest year, loudest/deepest transmissions, top family). Generated by `scripts/build_eras.py` (every figure recomputed and asserted); drives `eras/<id>.html` (schema: `data/v1/schema/eras.json`)

## Live functions — The Signal (Vercel, wave B)

Unversioned server functions, same-origin only (`fetch("/api/stats")` needs no
CORS). Every response uses the standard envelope (`ok`, `data`, `meta` with
`service:"aster-signal"`, `generated_at`, `source`, `request_id`; schema:
`data/v1/schema/envelope.json`). All `GET`s edge-cache 10 minutes
(`s-maxage=600, stale-while-revalidate=86400`); 60 requests/min/IP. The static
`data/v1/` files are the honest fallback — the frontend tries the function
first (7s timeout) and keeps the published static data with a "cached ·
updated HH:MM" badge when the function is cold or down (see
`assets/js/api-client.js`, `assets/js/signal.js`). Numbers only — no content,
no lyrics, no bio facts.

- `GET /api/health` — service status: `ok`/`degraded` (never 5xx), per-instance
  uptime, the function roster (`health`, `stats`, `uploads`, `cron/signal`),
  `data_freshness` per static dependency vs the 24h SLA, boolean-only checks
  (`static_fallback_present`, `cron_secret_configured`, `github_token_configured`).
- `GET /api/stats` — fresh numbers dashboard payload, computed live from the
  latest committed snapshot: `{tracks_captured, total_plays, snapshot_at,
  top_tracks[{title, plays, delta_7d}], source, delta_baseline_at, freshness}`.
  `delta_7d` is null until a week of history exists (honest gap, never
  interpolated). `freshness` = `{checked_at, snapshot_at, age_hours, status,
  sla_hours}`; a snapshot older than the 24h SLA answers with `degraded: true`
  and a plain-words note (latest verified capture, never presented as live).
  Fallback: `data/v1/stats-snapshots.json`.
- `GET /api/uploads?since=&limit=` — new uploads since an ISO date (default
  30d ago; `?since=` garbage → 400 `BAD_INPUT`; `?limit=` clamped 1–200):
  `{since, count, uploads:[{title, uploaded_at, url, first_seen_at}],
  checked_at, newest_upload_at, freshness}`, newest-first, titles + dates +
  permalinks only. `newest_upload_at` is the newest upload on record (full
  log, not the `?since` window). Fallback: `data/v1/uploads.json` (185 seeded
  rows).
- `GET /api/cron/signal` — daily (UTC, `0 16 * * *`) incremental refresh:
  SoundCloud api-v2 pull, play-count snapshot, new-upload detection, commit
  `refresh-status.json` + snapshot row on change only. Requires
  `Authorization: Bearer <CRON_SECRET>` (Vercel sends it automatically; 401
  otherwise); 60s duplicate cooldown; idempotent. Read-only until
  `GITHUB_REPO_TOKEN` is set — then it returns fresh data in the envelope
  without persisting (`read_only:true`).

Full hookup, env vars, cost rules, cold-start behavior, and rollback live in
`GO_LIVE.md`. Not deployed until the user approves.

## Publication rule

`research_status` gates everything. While it reads `PENDING`, no artist facts
are published — the site renders its designed "assembling the archive" state.
Facts enter only from verified public platform pages (Spotify, Apple Music,
SoundCloud, YouTube, etc.). Unverified claims are never published; identity
drift (a platform URL pointing at a different artist) escalates to research.

## Cover art

Discography entries carry an `artwork` URL sourced from the iTunes Search API
(`artworkUrl100`, upgraded to 600×600 via Apple's standard size pattern) and
hotlinked from Apple's CDN (`*.mzstatic.com`). Verified 2026-10-11: all 34
release artworks resolve with `image/*` content types. The site renders them
with `loading="lazy"` and falls back to a monogram tile if a URL ever dies.
Releases with no artwork simply omit the field — no placeholders.

## Provenance

Every discography entry carries a `source` string naming the platform/profile
the record came from and the verification date. All 34 distributor releases:
`Apple Music profile 1466301103 ("Aster Da Master") · iTunes Search API primary
metadata · verified 2026-10-11`. The site renders this as a small provenance
line on every discography card and in each release page's Provenance block.

## SoundCloud vault

`type: "SoundCloud-only"` marks tracks from the official SoundCloud profile
(https://soundcloud.com/asterdamaster), not distributor metadata. The full
catalog was verified 2026-10-11 via a read-only live-browser pass: **185
tracks** (2018:39 / 2019:36 / 2020:15 / 2021:13 / 2022:12 / 2023:26 /
2024:20 / 2025:17 / 2026:7), each with title, upload date, and a play-count
snapshot (play counts drift over time; the capture date is stated on every
page). Per-track SoundCloud URLs are not published (slugs not resolved by the
capture); every vault entry links the official profile. The top-level
`vault` object carries the profile facts (display name, followers, location,
bio) and capture date. The bio line "somelowlifes / Litemode Trilogy OTW" is
recorded under top-level `upcoming` as teased-not-confirmed. Vault entries
never carry lyrics — titles only.
Research notes: `~/workspace/research_notes/aster-soundcloud-20261011/report.md`
and `tracks.json` (the captured catalog).

- The homepage's **Numbers** section (VIII) is a live stats dashboard computed
  client-side from `data/artist.json`: total SoundCloud plays (257,394 as of the

  `codex/<slug>.html` deep-dive pages (schema:
  `data/v1/schema/codex-families.json`).
